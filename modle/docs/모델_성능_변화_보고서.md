# 서울대공원 방문객 예측 모델 성능 변화 보고서

작성일: 2026-05-13  
검증 구간: 2025-05-01 ~ 2025-07-31  
우선 목표: 실제 혼잡일을 예측 상위 위험일로 잘 올리는 것  
주요 우선 지표: NDCG@20, Recall@20, Precision@20  

## 1. 지표 해석 기준

| 지표 | 의미 | 해석 |
| --- | --- | --- |
| MAE | 실제 방문객 수와 예측 방문객 수의 절대 오차 평균 | 낮을수록 좋음 |
| RMSE | 큰 오차에 더 큰 벌점을 주는 평균 오차 | 낮을수록 좋음 |
| MAPE | 실제값 대비 오차율 평균 | 낮을수록 좋음 |
| R2 | 실제 변동성을 모델이 설명하는 정도 | 높을수록 좋음 |
| Precision@20 | 예측 상위 20일 중 실제 혼잡일 비율 | 높을수록 좋음 |
| Recall@20 | 실제 혼잡일 중 예측 상위 20일에 잡힌 비율 | 높을수록 좋음 |
| NDCG@20 | 혼잡한 날을 예측 순위 상단에 잘 배치했는지 | 높을수록 좋음 |

이 프로젝트는 단순 평균 오차보다 "혼잡일을 놓치지 않는 것"이 중요하므로, 튜닝 기준은 주로 NDCG@20과 Recall@20을 우선했다.

## 3. 1단계 혼잡일 분류 모델 튜닝

### 목적

1단계 모델은 날짜별로 "혼잡일일 가능성"을 먼저 분류한다. 이 값은 2단계 방문객 수 예측 모델에 `혼잡일확률`, `혼잡일예측라벨`로 전달된다.

### 튜닝 방식

- 처음에는 RMSE 최소화를 기준으로 좌표 탐색을 수행했다.
- 이후 사용 목적을 "혼잡도 우선"으로 다시 잡고, NDCG@20 최대화를 기준으로 100회 무작위 탐색을 수행했다.
- 동률일 경우 RMSE, MAE 순으로 비교했다.

### 최종 선택 파라미터

```python
CLASSIFIER_PARAMS = {
    "loss_function": "Logloss",
    "depth": 6,
    "learning_rate": 0.06,
    "iterations": 800,
    "l2_leaf_reg": 5.0,
    "random_seed": 42,
    "verbose": False,
    "allow_writing_files": False,
}
```

### 성능 변화

| 비교 | MAE | RMSE | R2 | NDCG@20 |
| --- | ---: | ---: | ---: | ---: |
| 기준 모델 | 3266.38 | 4620.77 | 0.7312 | 0.8825 |
| RMSE 우선 탐색 최고 | 2839.21 | 4188.74 | 0.7791 | 0.8952 |
| 혼잡도 우선 100회 탐색 최고 | 3160.34 | 4419.26 | 0.7541 | 0.9399 |

RMSE 우선 탐색은 평균 오차가 더 작았지만, 혼잡일 순위 성능은 낮았다. 최종 목적이 혼잡일 탐지였기 때문에 NDCG@20이 높은 `depth=6`, `learning_rate=0.06`, `iterations=800`, `l2_leaf_reg=5.0`을 선택했다.

## 4. 결측값 보정 모델 튜닝

### 목적

방문객 데이터에는 긴 결측 구간이 있었다.

- 2016-12-18 ~ 2017-03-29
- 2019-09-07

결측값 보정 모델은 이 구간의 방문객 수를 학습 데이터에 자연스럽게 채우기 위한 보조 모델이다.

### 튜닝 방식

- 기준 모델에서 시작해 `depth`, `learning_rate`, `iterations`, `l2_leaf_reg`, `min_data_in_leaf`, `random_strength`를 하나씩 변경했다.
- 기준은 NDCG@20 최대화였다.
- 1라운드에서 후보 12개를 모두 비교했지만 기존값보다 좋은 결과가 나오지 않아 중단했다.

### 최종 선택 파라미터

```python
IMPUTATION_MODEL_PARAMS = {
    "loss_function": "RMSE",
    "depth": 6,
    "learning_rate": 0.05,
    "iterations": 700,
    "l2_leaf_reg": 5.0,
    "min_data_in_leaf": 5,
    "random_strength": 1.0,
    "verbose": False,
    "random_seed": 42,
    "allow_writing_files": False,
}
```

### 성능 변화

| 단계 | MAE | RMSE | R2 | NDCG@20 | 판단 |
| --- | ---: | ---: | ---: | ---: | --- |
| 기존 결측값 보정 설정 | 3225.01 | 4313.09 | 0.7658 | 0.9300 | 최종 유지 |
| 최고 후보 | 3225.01 | 4313.09 | 0.7658 | 0.9300 | 기존과 동률 |

결측값 보정 모델은 파라미터를 바꿔도 전체 성능 개선이 없었다. 따라서 기존 설정을 유지했다.

## 5. 2단계 최종 방문객 수 예측 모델 튜닝

### 목적

2단계 모델은 최종 방문객 수를 예측한다. 1단계 혼잡일 분류 모델의 출력값을 함께 사용한다.

### 튜닝 방식

- 1단계 혼잡일 분류 모델은 확정값으로 고정했다.
- 2단계 CatBoostRegressor의 `depth`, `learning_rate`, `iterations`, `l2_leaf_reg` 조합을 100회 무작위 탐색했다.
- 1차 기준은 NDCG@20, 동률 기준은 RMSE와 MAE였다.

### 최종 선택 파라미터

```python
REGRESSOR_PARAMS = {
    "loss_function": "RMSE",
    "depth": 10,
    "learning_rate": 0.04,
    "iterations": 1200,
    "l2_leaf_reg": 8.0,
    "random_seed": 42,
    "verbose": False,
    "allow_writing_files": False,
}
```

### 성능 변화

| 단계 | MAE | RMSE | R2 | Precision@20 | Recall@20 | NDCG@20 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 1단계 튜닝 후 | 3160.34 | 4419.26 | 0.7541 | 0.65 | 0.9286 | 0.9399 |
| 2단계 최종 튜닝 후 | 3214.38 | 4509.65 | 0.7440 | 0.65 | 0.9286 | 0.9478 |

2단계 튜닝 후 MAE와 RMSE는 약간 나빠졌지만, NDCG@20은 0.9399에서 0.9478로 상승했다. 즉 전체 평균 오차보다 "혼잡한 날을 상위 위험일로 배치하는 능력"을 우선한 선택이다.

## 6. 대공원역 방문 데이터 추가 조사

### 수집 및 결합

서울 열린데이터광장의 지하철 승하차 CSV를 이용했다. 데이터에서 대공원역은 `4호선`이 아니라 `과천선 / 대공원`으로 들어가 있었다.

- 수집 범위: 2015-01-01 ~ 2025-07-31
- 병합 일수: 3762일
- 추가 데이터: 대공원역 승차, 하차, 승하차합
- 저장 파일: `backend/data/artifacts/external_transport/seoul_grand_park_visitors_with_daegongwon_subway.csv`

### 방문객 수와 대공원역 승하차의 상관관계

| 구간 | N | Pearson | Spearman | 평균 방문객 | 평균 승하차 |
| --- | ---: | ---: | ---: | ---: | ---: |

대공원역 당일 승하차 데이터는 방문객 수와 매우 강한 관계가 있었다. 하지만 미래 예측 시점에는 예측 대상 날짜의 실제 대공원역 승하차를 알 수 없다. 따라서 최종 서비스 모델에는 직접 넣지 않았다.

과거 교통량은 날씨보다 약간 더 높은 연관도를 보였다. 그러나 장기 미래 예측에서는 1일 전, 7일 전 교통량도 아직 모르는 값이 될 수 있으므로 최종 서비스 모델에서 제외했다.

## 7. 대공원역 데이터를 넣었을 때의 성능

대공원역 데이터를 모델에 직접 넣으면 수치상 성능은 좋아졌다. 다만 이 실험은 `당일 대공원역 승차/하차/승하차`를 사용했기 때문에 실제 미래 예측 서비스에는 사용할 수 없다.

| 모델 | MAE | RMSE | MAPE | R2 | Precision@20 | Recall@20 | NDCG@20 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 2단계 최종 튜닝 모델 | 3214.38 | 4509.65 | 194.84 | 0.7440 | 0.65 | 0.9286 | 0.9478 |
| 당일 대공원역 데이터 직접 투입 | 2497.10 | 4069.31 | 135.44 | 0.7915 | 0.65 | 0.9286 | 0.9418 |

방문객 수 오차는 크게 줄었지만, 이는 예측 대상 날짜의 실제 교통량을 알고 있다고 가정한 결과다. 실제 운영에서는 불가능하므로 참고용 성능으로만 남겼다.

## 8. 실제 미래 예측용 모델로 변경

### 변경 이유

기존 모델은 다음과 같은 방문객 lag/rolling feature를 사용했다.

```text
지연값_1
지연값_7
지연값_30
지연값_365
이동평균_7
이동평균_30
이동표준편차_7
이동표준편차_30
```

이 값들은 과거 검증에서는 실제 방문객 수로 만들 수 있지만, 긴 미래 예측에서는 중간 날짜의 실제 방문객 수를 알 수 없다. 기존 방식은 앞서 예측한 방문객 수를 다음 날짜의 입력값으로 다시 사용하는 반복 예측 구조였다. 이 방식은 장기 예측으로 갈수록 오차가 누적될 수 있다.

### 최종 서비스 모델 feature

최종 서비스 모델은 미래 시점에도 안정적으로 구할 수 있는 feature만 사용하도록 변경했다.

```text
날짜
요일
주말 여부
공휴일 여부
연휴 여부
방학/성수기 여부
행사 여부
날씨 API 예보 평균기온
날씨 API 예보 강수량
강수 여부
폭우 여부
너무 추움 여부
너무 더움 여부
```

### 성능 변화

| 모델 | MAE | RMSE | MAPE | R2 | Precision@20 | Recall@20 | NDCG@20 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 2단계 최종 튜닝 모델 | 3214.38 | 4509.65 | 194.84 | 0.7440 | 0.65 | 0.9286 | 0.9478 |
| 실제 미래 예측용 모델 | 3347.89 | 5414.60 | 179.34 | 0.6309 | 0.55 | 0.7857 | 0.8292 |

성능은 하락했다. 하지만 이 결과가 실제 서비스에서 기대할 수 있는 성능에 더 가깝다. 기존 모델은 성능이 좋아 보였지만, 장기 미래 예측에서는 예측값을 다시 입력으로 쓰는 구조라 운영 안정성이 낮았다.

## 9. 최종 판단

### 성능만 보면

```text
당일 대공원역 데이터 직접 투입 모델
> 2단계 하이퍼파라미터 튜닝 모델
> 실제 미래 예측용 모델
```

### 실제 서비스 가능성까지 고려하면

```text
실제 미래 예측용 모델
> 2단계 하이퍼파라미터 튜닝 모델
> 당일 대공원역 데이터 직접 투입 모델
```

대공원역 데이터는 방문객 수와 강하게 연관되어 있으므로 중요한 외부 데이터다. 다만 최종 예측 모델에 직접 넣으려면 다음 중 하나가 필요하다.

1. 미래 대공원역 이용량을 따로 예측하는 보조 모델을 만든다.
2. 당일 오전 실시간 대공원역/주차 데이터를 받아 "당일 보정 모델"로 사용한다.
3. 현재처럼 분석용 데이터로만 보관하고, 최종 장기 예측 모델은 날짜/행사/날씨 중심으로 운영한다.

현재 프로젝트의 조건에서는 3번이 가장 안전하다.
